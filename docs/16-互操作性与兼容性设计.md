## 1. 三层判据

「协议库能跑」与「能被现有网络接纳」是两件事，必须分三层评估：

| 层 | 问题 | 结论 |
|---|---|---|
| ① 线协议层 | 握手、消息、分片、tracker 报文字段是否互通 | **基本完全兼容** |
| ② 会话与身份层 | PeerID、private flag、做种、积分、端口可达 | **需要我们在 P0 起显式实现** |
| ③ 网络准入层 | 私有 tracker 白名单、社区规则、生态反吸血 | **代码解决不了，也不该硬闯** |

## 2. BT 线协议覆盖

`anacrolix/torrent` v1.61.x 官方 BEP 清单：**3 / 4 / 5 / 6 / 7 / 9 / 10 / 11 / 12 / 15 / 19 / 20 / 23 / 27 / 29 / 40 / 41 / 42 / 43 / 47 / 52 / 54 / 55**，另含 MSE/PE 加密、uTP、WebTorrent(WebRTC)、WebSeed、BT v2 混合种子、打洞、智能封禁、IPv6、HTTP/UDP tracker 客户端与服务端、scrape。2014 年起生产使用，Gopeed / bitmagnet / TorrServer 等在运行。

| 对象 | 判定 |
|---|---|
| qBittorrent / Transmission / libtorrent 系公网 peer（双向做种与下载） | ✅ 无阻碍 |
| 公开 HTTP / HTTPS / UDP tracker、compact peer list、多 tracker 分层、IPv6 扩展、scrape、passkey（只是 announce URL 的一部分） | ✅ 协议层通 |
| `private=1`（BEP 27） | ✅ 库已实现，需我方确保关闭 DHT/PEX/LSD |
| **LSD（BEP 14，局域网组播发现）** | ❌ 库未实现（issue #248 自 2018 未合）；需自补几十行组播或依赖 tracker/DHT |
| **Super-seeding（BEP 16）** | ❌ 库未实现 |
| **BT v2** | ⚠️ 只使用 **hybrid**；v1-only 客户端无法加入纯 v2，tracker 对 `btmh` / 双 infohash 双 announce 支持仍不整齐，部分实现明确把「与 libtorrent/qBittorrent v2 live 互操作」列为未完成 → 产品默认 v1/hybrid |
| 迅雷 P2SP | ❌ 私有协议，仅 `thunder://` 解码 |

## 3. eD2k 线协议覆盖

`goed2k`（MIT，v0.1.0，Gopeed v1.9.3 采用）实现：多 eD2k 服务器 + `server.met`、Kad4/KadV6 bootstrap 与搜源发布、Source Exchange、Low ID 回调、AICH、Secure Ident（RSA 2048）、**积分系统**（`PeerCreditManager` / `ScoreRatio` / `client_credits.go`）、zlib 上传压缩、OfferFiles / Kad 发布、CryptLayer 协议混淆、Collection 链接。aMule/eMule 主要互通路径基本覆盖。

**当前态补记（2026-11-27）**：上述为 2026-11-21 勘察时的库能力口径；本仓库 fork 现已
补齐三条生产通路：① 服务器 port callback 的 6 字节 Hello 头握手、默认持续重连与
登录前 `user_hash` 恢复（`docs/25` §13.2）；② 客户端间 **Source Exchange 2**
（`0x83/0x84`，版本 4，v1/v2/v4 条目，高 ID 按 hybrid ID 拨号；§13.3）；
③ 进行中文件 `OfferFiles` + 引擎上传字节上报 `tasks.bytes_uploaded`（§13.4），
使 eMule 队列信用不再只进不出。**边界**：真机尚未收到 AnswerSources2（当前对端
多为完整文件源），队列优先级收益未做定量门禁；ED 门禁与 P3 发布结论不变。

### 3.1 与 eMule 客户端的能力对照矩阵（2026-11-27 复核）

以本机 eMule `srchybrid` 源码为基线，对本项目已落地的 16 项客户端能力逐项做**字节级**
复核（报文布局、字段顺序、状态机取值、判定布尔式），而不只对照「功能是否存在」。
结论分三档：

- **一致**：线上字节与状态语义与 eMule 相同，对端可正常解析；
- **已修正**：本轮发现偏差且会导致对端丢弃报文或语义错误，已按基线改正；
- **设计差异**：协议可通，但资源归属、评分口径、默认开关等策略有意不同。

#### 3.1.1 线协议偏差（8 项，已全部修正）

| 能力 | eMule 基准行为 | 原实现偏差 | 修正后 |
|---|---|---|---|
| SecureIdent 签名报文 | `OP_SIGNATURE` 体为 `<len 1><sig N>[<bySigIPUsed 1>]`，**不重复携带公钥**（`BaseClient.cpp::ProcessSignaturePacket`） | 签名包里又塞了一份公钥，对端按 `nSize` 判定长度不符直接丢弃 | 报文体改为纯签名（+ 可选 IP 类别字节），公钥只在 `OP_PUBLICKEY` 出现 |
| SecureIdent 签名内容 | 签 `<验证方公钥 DER><验证方挑战 4B>`（`CClientCreditsList::VerifyIdent` 用 `m_abyMyPublicKey`） | 只签 4 字节挑战 | 签名数据改为「对端公钥 + 对端挑战」，双向对称 |
| SecureIdent 状态机 | `OP_SECIDENTSTATE`：`1` = 只需签名，`2` = 需要公钥 + 签名（`IS_SIGNATURENEEDED` / `IS_KEYANDSIGNEEDED`） | 1/2 语义写反；且只验对端、从不主动发自己的公钥/签名 | 常量纠正，补齐主动发起与双向握手；会话级持久 RSA 1024 身份（重启不换身份） |
| Server UDP 能力协商 | 登录后由 `OP_SERVERIDENT`（`0x41`）下发 `ST_UDPFLAGS`/`ST_UDPKEY`/`ST_UDPKEYIP`，据此决定加密与源请求 opcode（`Server.cpp::GetServerKeyUDP`） | 完全未实现 `0x41`，三个 tag 恒为空 → UDP 加密与 `OP_GLOBGETSOURCES2` 选择失去依据 | 新增 `protocol/server/server_ident.go` 并接入会话；key 仅在 `SRV_UDPFLG_UDPOBFUSCATION` 置位且 keyIP 与本机公网 IP 一致时安装 |
| Server UDP 源请求 | 有 `SRV_UDPFLG_EXT_GETSOURCES2` 用 `0x94`（带 size），否则 `0x9A`（仅 hash），两者都无则不发 | 固定发 `0x94` | 按服务器宣告的能力降级选择 |
| Server UDP 收包 | 每包现取 key（`m_dwServerKeyUDP` 可变）；每条记录前可重复 `<E3 opcode>` 子包头 | 启动时快照 key → 登录后装 key 永不生效；解析用逐字节滑动搜头，payload 中出现同字节对即错位 | 逐包读 key；严格按头部解析并支持重复子包头（`0x9B` 多记录同包） |
| KAD 低 ID 回调 | `KADEMLIA_CALLBACK_REQ`（`0x52`）= `<check 16><file 16><TCPPort 2>`，共 34 字节；`Process_KADEMLIA_CALLBACK_REQ` 对更短的包直接抛错 | 只发 2 字节端口；且未实现 `OP_CALLBACK`（`0x99`）转发 | 按 34 字节编码；补 `OP_CALLBACK` 转发（buddy 经已有 TCP 连接告知被请求方 `<check><file><ip><port>`）；搜源命中 firewalled 源时向返回者发起回调 |
| AICH 失败应答 | 无法提供恢复数据时回 16 字节裸 hash（无 part/masterhash 字段） | 解析器按完整结构读，字段缺失报错，被当作坏包丢弃 | 识别为 `Failed`，停止对 AICH 的请求并回退整块重下 |
| IPFilter 等级判定 | `CIPFilter::IsFiltered` 用 `level < 过滤等级`（**严格小于**），`0.0.0.0` 不放行判定 | 用 `<=`，等级恰为 127 的条目被误杀 | 改为 `<`；未指定地址直接放行；默认等级 127 与 eMule 一致 |
| 出站压缩块 | `compress2(..., Z_BEST_COMPRESSION)`；分片长度 `total/(total/10240)` 均分并合并尾片（`CreatePackedPackets`） | 默认压缩级别 + 固定 10 KiB 切片，尾片可能过小 | 改为最高压缩级别与均分片算法；压不小则回退明文 |
| 聊天报文 | `MAX_CLIENT_MSG_LEN`（450 字节）；接收侧校验 `length + 2 == size` | 上限 8192，且不校验长度自洽 | 上限 450，长度不自洽即拒绝 |
| UDP 本地绑定端口 | 绑定配置的 eD2k UDP 端口（`CClientUDPSocket`），对端看到的源端口即该端口 | 绑 `TCP 端口 + 4`，与服务器/对端记录的源端口不一致 | 改用 `ed2k.udpPort` |

#### 3.1.2 协议一致、但存在设计差异（8 项）

| 能力 | eMule 行为 | 本项目行为 | 互通影响 |
|---|---|---|---|
| A4AF（源自动转移） | 源**单一归属**某个任务，可按优先级回迁；不复制 | 源**复制**给所有缺源任务，`NoFileStatus` 时先转源再断开 | 无协议影响；可能对同一源发起重复请求（本端多耗一点连接槽） |
| 搜索垃圾评分 | `searchspam.met` 规则库，0..100 分，由用户配置阈值 | 内置启发式（伪装扩展名 / 异常体积 / 关键词堆砌），0..5 星 | 无；评分只在本端展示与排序用，不上线 |
| KAD 源发布 | 定期 republish（约 5 小时）维持曝光 | 文件变为可分享时发布一次，登录拿到 High ID 后补发一次 | 无；长期在线文件的 KAD 曝光弱于 eMule |
| 好友与聊天 | 接受任意客户端消息 + captcha 防骚扰；好友仅作收藏 | 仅接受好友列表内消息；`OP_MESSAGE` 报文格式与 eMule 相同 | 无；策略更严，可能收不到陌生人的求助消息 |
| UPnP 端口映射 | 默认开启 | 已接线（`ed2k.enableUPnP`），默认关闭 | 无；未开时 Low ID，源数量偏低但功能正常 |
| 文件预览 | part 级：完成的首个 part 即可预览 | 要求「从头连续完成」至少一个完整 part（9.5 MB） | 无；与 eMule part 语义一致 |
| Collection 集合 | 文本 `.emulecollection` + 二进制 v1/v2（tag 布局 `packets.cpp:472`） | 两种格式均实现，写文本、读文本 + v1/v2 | 无；可被 eMule 直接导入 |
| 分时限速 | eMule 自身无此功能（aMule 有带宽调度） | `global.bandwidthSchedule` 窗口 + 30s 评估，支持跨夜与工作日/周末 | 无；纯本地策略 |

#### 3.1.3 复核结论

1. **线协议层面 16/16 可互通**：修正后不存在会被对端按长度/字段校验丢弃的报文。
2. 8 项设计差异均为**本端策略**（归属、评分、开关、周期），不改变线上字节，
   因此不影响与 eMule / aMule 的连接与传输。
3. **AICH 仍只做下载侧**：能请求并校验恢复数据，但不生成 hashset 为他人提供恢复数据，
   因此 MiscOptions 不宣告 `AICHVersion`——宣告后对端会白跑一次请求却拿不到数据。
4. 回归覆盖：本轮新增 11 个测试（ServerIdent 能力位、UDP 多子包/内嵌头、34 字节
   callback、`OP_CALLBACK` 往返、SecureIdent 签名线格式、IPFilter 边界、AICH 拒绝等），
   详见 `12` §3.2 的 ED-09..ED-13 与 `25` §14.4。

> 上述矩阵是**读码比对**结论；同一批代码在真实公网服务器与真实 eMule / aMule 客户端上的
> 执行结果见本文 §6.1「eD2k 真实服务器 / 真实客户端互通实测」，其中记录了该项复核
> 之后又暴露并修复的 4 处互通缺陷（登录缺 `CT_EMULE_UDPPORTS`、缺 `OP_GETSERVERLIST`、
> UDP 搜索缺 tag set、SecureIdent 公钥 1024 位超出 eMule `MAXPUBKEYSIZE=80`）。

## 5. 网络准入层：不由代码决定

### 5.1 私有 tracker
PT 普遍只白名单 qBittorrent / Transmission / rTorrent / Deluge 等特定版本，靠 PeerID + 扩展握手识别；未列入白名单的 `-GT0001-` 会被拒或标记。伪装 PeerID 违反站点规则，且 announce 时序、格式、统计交叉校验容易被反作弊识别。

**产品决策**：只声明「兼容标准 BT 网络，**不承诺 PT**」；确有需求时提供可选 BYO 适配器，把任务交给用户已安装的白名单客户端（qBittorrent WebUI），而非自己冒充。公网侧也有 PeerBanHelper 类按 PeerID/Client Name 黑名单 + 伪装检测 + 假进度检查的工具，诚实做种能缓解但无法保证。

### 5.2 eMule 网络现实
「能连上」≠「下得动」：积分是**双向、按客户端对**计分，新客户端 modifier 恒为 1.0，排在上传队列末尾，须先给别人上传才能攒信用；网络规模小，冷门文件常无在线源；0.50a 与社区版 0.72a 并存，部分 mod 有「不良客户端检测」。

**最大技术风险**：`goed2k` 为 AI 辅助开发的 v0.1.0 新库，官方文档明确写「尚未与真实 eMule 全版本做大规模互操作回归；生产环境建议先小范围试连」。Gopeed 是一个生产用例，但不等于全版本验证 → 必须靠 §6 套件兜底。

### 6.1 eD2k 真实服务器 / 真实客户端互通实测（2026-11-27）

驱动工具是 `cmd/uded2kpeerprobe`（本仓库自带，可复跑）：

```

它做四件事：登录真实 eD2k 服务器 → 关键词搜索挑文件 → 连接搜索结果里的真实客户端 →
记录对端客户端名/版本、SecureIdent 是否验证、进度与速率。

**实测目标**：`176.123.5.89:4725`（eMule Sunrise / Lugdunum，约 5 万用户，`udpFlags=0x0`）、
`57.128.161.24:6666`（Cyberchrist 18.1，`udpFlags=0x0000073b`，即同时宣告
`EXT_GETSOURCES`+`EXT_GETFILES`+`EXT_GETSOURCES2`+`LARGEFILES`+`UDPOBFUSCATION`）。
后者是全网少见的能力齐全节点，本轮 UDP 端到端验证即在它上面完成。

#### 6.1.1 实测暴露并修复的 4 处互通缺陷

| # | 缺陷 | 现场证据 | 修复 |
|---|---|---|---|
| 1 | 登录包缺 `CT_EMULE_UDPPORTS(0xF9)` | 登录 hex 到 `…83fb80000201` 即结束，服务器看到的 eD2k UDP 端口未知 | `NewLoginRequest` 补 tag，值 `udpPort<<16\|udpPort` |
| 2 | 从不发 `OP_GETSERVERLIST`，服务器因此从不发 `OP_SERVERIDENT` | 抓包只见 `IdChange`+`Status`+`Message`，无 `0x41`；eMule 源码注明该包仅在收到 `OP_GETSERVERLIST` 后下发 | `IdChange` 后发一次 `OP_GETSERVERLIST` |
| 3 | UDP 搜索用 `0x90` 但缺 tag set，且未按服务器能力选 opcode | eMule `CSearchResultsWnd::DoNewED2KSearch` 要求 0x90 = `<1 tag set><搜索树>` | 补 `CT_SERVER_UDPSEARCH_FLAGS(0x0E)` tag set，并新增 `UDPGlobSearchDatagram()` 按 `EXT_GETFILES`/`LARGEFILES` 选 0x90/0x92/0x98 |
| 4 | SecureIdent 身份是 1024 位（DER 162 字节），eMule `MAXPUBKEYSIZE=80` 直接丢弃 | 对端发来的公钥 78 字节；我们发 162 字节时日志只有 `public key stored`，永不出现 `verified` | 自实现 384 位 RSA（`rsa_ident.go`，`crypto/rsa` 拒绝 <1024 位），公钥 78–80 字节、签名 48 字节 |

补充修复（本轮新发现）：搜索结果/源请求可能在 `OP_SERVERIDENT` 到达**之前**发出，
此时能力位未知，opcode 静默降级为 legacy 0x98、UDP 查源则直接不发。
现按 eMule 的持久化做法补齐两层依据：
① `server.met` 的 `ST_UDPFLAGS(0x92)` 读取（`ServerMetEntry.UDPFlags()`）并在加载时预热会话缓存；
② 每次 `OP_SERVERIDENT` 回填缓存（`Session.RememberServerCapabilities`）；
③ 连接已解析过 ident 时以实况为准（`ServerConnection.HasServerIdent()`），避免用过期缓存覆盖
「这台服务器确实不支持 UDP」的事实。

#### 6.1.2 抓包证据（`dist/ed2k-interop/udp-search.pcapng`、`udp-cyberchrist.pcapng`）

**UDP 搜索请求**（`e3 90`）：

```

**UDP 搜索结果**（服务器回 `e3 99`，单帧一条记录）：

**2026-11-28 查源证据补强**：`docs/26` §4.8 把固定 ISO 哈希换成「每台服务器自己搜到的
热门文件哈希」后，8 台在线服务器 **8/8 全部回 `0x9B`**（第 9 台主动拒绝连接、不可达），
证实前几轮「6 台查源未回包」的根因是对端索引里没有该 ISO 的源，而非协议不兼容。
探针新增自动选热门哈希、按 opcode 计数的回包统计（`answer_opcodes_delta` 区分「回了但
解析失败」与「没回」）与 2 个单测。这条结论只收紧了「无源」这一边界，不改变 UDP 互通
能力判定，专项仍保持收口归档。

**2026-11-28 SX2 专项（结论修正）**：此前结论表写「SX2 over TCP 发出未收到应答，多数
服务器不回 `0x84`」——这个表述有两处需要更正：① `OP_REQUESTSOURCES2`(0x83) /
`OP_ANSWERSOURCES2`(0x84) 是 **客户端与客户端之间**的源交换（走 `OP_EMULEPROT` 0xC5），
不是服务器协议，服务器从不参与 0x84；② 未收到应答并非请求格式或时序缺陷。

逐字节核对与真机抓包（`dist/ed2k-interop/peers.pcapng`）确认：我们发出的 0x83 为
`c5 14 00 00 00 83 04 00 00 <16B hash>`，即 0xC5 封装 + 长度 20 + 内部 opcode 0x83 +
version 4 + reserved 0 + hash，与 aMule `DownloadClient.cpp` 的组包及上游 `goed2k/core`
文档一致；触发时机在 Hello/ExtHello/SecureIdent/FileStatus 全部完成之后（先 0x58 文件
请求、0x4F 文件状态，确认对端持文件后再发 0x83），也不是「握手未完成」。

未回 0x84 的根因在**对端角色与状态**：eMule/aMule 只在「本连接正在为该 hash 提供上传、
且自己持有可交换的源列表」时才组应答。aMule `CPartFile::CreateSrcInfoPacket()` 在
`m_SrcList.empty()` 时直接 `return NULL`，随后 `ClientTCPSocket.cpp` 因 `tosend==NULL`
不发送任何包；同时还有 `GetLastSrcReqTime()` 的时间窗限制。真机里我们连的是**正在给我们
提供下载的完整源节点**（`FileStatusAnswer pieces=0 have=0`），它们自己并不下载该文件、
没有 srcList 可交换，因此静默——这是协议设计使然，不是互通缺陷。抓包里 0x83 发出 2 次、
0x84 零次，但对端 0x54 AcceptUpload / 0x46 SendingPart 正常流入，连接与传输均健康。

我方实现已按同一语义对齐：应答侧 `HandleRequestSources2` 在无源时不发包（单测
`TestHandleRequestSources2WithoutSourcesSendsNothing`），有源时回 v4 应答
（`TestHandleRequestSources2OffersKnownSources`）；请求侧固定 `SOURCEEXCHANGE2_VERSION=4`
（对端会 clamp 到自身支持版本）。因此 SX2 的**报文发送与接收解析能力均 PASS**，
真机未回 0x84 属于「应答前提未满足」，保留为边界事实而非缺陷清单。

**2026-11-28 真机补充**：RC4 信封与 `0x92` 分支已在真实公网服务器上闭环。抽样服务器
`OP_SERVERIDENT` 都不带 `ST_UDPKEY`，但 eMule 还有第二条路径：向 TCP+12 发 crypt ping，
从 `OP_GLOBSERVSTATRES` 取 key。真机实测拿到 key `1838661081`，其后 `0x92` 请求与
`0x99` 回包都是密文且正确解析。详见 `26` §4.4 与 `dist/ed2k-interop/run14.log`、
`udp92-encrypted.pcapng`。

**2026-11-28 补充**：RC4 信封与 0x92 分支已完成协议级闭环——用独立实现的 eMule 编解码器
做字节级交叉验证，并用真实 UDP socket 跑通加密请求/回包全链路；验证中还修复了第 5 处缺陷
（UDP key 原按 `clientID` 校验，eMule 实际按 `OP_IDCHANGE` 报告的公网 IP 校验，LOW_ID 客户端
的 key 会全部被误拒）。另外修复 crypt ping 请求被错误加密的问题：eMule raw packet 不加密，
加密请求会让服务器把密文字节当 challenge，回包永远解不开。完整格式、证据、复跑命令与仍存
边界见 [`26` eD2k UDP 互通验证报告](26-eD2k-UDP互通验证报告.md)。

**2026-11-28 legacy 与抽样补充**：`0x98` 搜索、`0x9A` 查源已在 Cyberchrist 上用强制
opcode 跑通真机往返（分别回传 10 个加密 `0x99`、1 个目标哈希的加密 `0x9B`）；抽样中的
9 台 UDP 能力服务器全部登录成功且 UDP 搜索有回包，3 台对已知 ISO 哈希回传了 `0x9B`，
5 台经 crypt ping 安装了 server key。自动选择 `0x92`/`0x9A` 的服务器仍未找到，
6 台查源未回包当时只记录事实、不外推原因；**v1.5 补强轮已用热门哈希坐实根因是无源（见下）**。第二轮复跑把强制 `0x92` 扩展到 9/9
服务器均有回包；自动查源与强制 `0x9A` 仍是同一批 3 台，crypt key 三轮分别为
5/9、7/9、8/9，说明 `0x97` 下发 key 跨会话不稳定。详见 `26` §4.5 / §4.6 / §4.7。


## 7. 产品文案口径（法务会签）

## 8. 兼容性结论表

| 对象 | 判定 |
|---|---|
| qBittorrent / Transmission / libtorrent 等公网 peer | ✅ 双向互通 |
| 公开 HTTP/UDP/HTTPS tracker、scrape、passkey、private flag | ✅ 协议层通 |
| 私有 tracker 准入 | ⚠️ 技术可通、规则不接纳，**不承诺** |
| aMule / eMule 客户端 | ✅ 线协议通；⚠️ 速度受积分、Low ID、混淆、源数量支配 |
| HTTP / FTP / SFTP 镜像、Metalink 清单 | ✅ 标准协议 |
| 迅雷 P2SP / 高速通道 / 离线下载 | ❌ 私有协议，仅链接解码 |
| DRM 内容 | ❌ 明确不支持 |

**WBS 8 / 9 实现边界（2026-11-10）**：`thunder://` / `flashget://` / `qqdl://` 解码与
Metalink v3/v4 XML、RFC 6249 头已落地为内置纯 Go Resolver；FTP / FTPS / SFTP 的
Transport 已于 WBS 9 落地，上表「HTTP / FTP / SFTP 镜像」中的三类镜像现在都能被
`transport.Select` 选中并实际下载（`12` §3.3 有回环真实协议栈用例）。
**仍不支持**：多 `<file>` 清单、远端 `.meta4` URL 抓取、FTP 主动模式、FTPS 数据通道
TLS session 复用、无 host key pin 的 SSH 连接；与真实公网 FTP/SFTP 服务器的互操作矩阵
尚未执行。因此对外仍只能写「支持 Metalink 多源清单解析」「支持 FTP / FTPS / SFTP 下载」，
不得写「完整 Metalink 生态」「兼容所有 FTP 服务器」「迅雷加速」。

**WBS 7 实现边界（2026-11-10）**：BT / 磁力已由 `internal/transport/bt` 落地（§4、
