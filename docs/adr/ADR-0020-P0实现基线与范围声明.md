# ADR-0020 P0 实现基线与范围声明

- **状态**：Accepted（2026-11-09 P0 里程碑评审批量批准）
- **日期**：2026-11-08
- **决策者**：架构组
- **关联需求与文档**：`03` §7/§8、`04` §11、`05` §12、`06` §10、`07` §8、`10` §7、`11` §10、`12` §9、`13` §12、`14` §9、`15` §10/§11、`CHANGELOG.md` `0.1.0`
- **前置 ADR**：ADR-0001、0002、0012、0013、0015、0016、0019

## 背景（问题、约束、已核实事实）

`14` WBS 1–6 的 P0 基线在 2026-11-08 完成编码。此前仓库只有规划文档，P0 一旦落地就出现三类需要归档的偏差：

1. **规范本身有笔误**：`05` §2 把 `ResolveContext.Guard` 写成 `*security.SSRFGuard`（会让 `core` 反向依赖实现包，违反 `05` §1）；`ChunkWriter` 缺 `Next()` / `Release()`（与「`chunks` 表为唯一真值源」冲突）；`05` §4 图示与表格对「任意状态可取消」表述不一致。
2. **规范未定义的细节**：`06`/`07` 提到 `bitfield(hex)` 却没规定字节数；`07` §1 说「远程需显式开启 + token」但没写清违规时是拒绝启动还是降级监听。
3. **P0 有意的实现取舍**：凭据存储用进程内参考实现而非 OS 钥匙串；`POST /tasks` 不内嵌 `Resource` 预览；最小 UI 是单文件占位；`07` §5 的 L1 facade 完全不实现；部分非功能优化（批量刷盘、事件保留清理、慢启动动态扩连）延后。

若不写 ADR，这些差异会被后来的开发者误读为「实现缺陷」或「文档过时」，甚至按旧规范把代码改回去（例如重新让 Transport 自己算分片边界）。

## 决策（一句话结论 + 具体规定）

**P0 是「骨架 + 一条 HTTP(S) 直链」的可运行基线，不是功能完整版。** 所有规范与实现之间的差异必须在 ADR-0020 中显式登记、在对应 `docs/` 文档中标注、在 `CHANGELOG.md` 中留痕；未登记的差异视为缺陷。

具体规定：

### 1. 以代码为准修正三处规范笔误（`05` v0.2）

| 项 | 修正后 |
|---|---|
| `ResolveContext.Guard` | `core.URLGuard` 接口（`Check` / `DialContext` / `MaxRedirects`），实现在 `internal/security`；`core` 保持零实现依赖 |
| `ChunkWriter` | 增加 `Next(ctx) (Chunk, bool, error)` 与 `Release(ctx, c, err) error`；Transport 只领取/归还，不自算分片边界、不自定重试次数 |
| Task 状态机 | `Cancel` 允许从**任意非终态**进入 `Canceled`；终态不可再迁移。以 `internal/core/task.go:transitions` 为权威 |

同时明确 `Release` 语义：取消类错误与可重试错误回 `pending`；不可重试且达上限才 `failed`；`failed` 仅由用户显式 `Resume` 或崩溃恢复重置。

### 2. 补齐两处未定义细节

- **位图编码**：`bitfield` = `ceil(numPieces/8)` 字节、高位在前、小写 hex；`done`/`verified` 均置位。3 片首片完成为 `80`（不是 `8000`）。见 `06` §10。
- **远程鉴权 fail closed**：非回环监听且 `remoteToken` 为空时 `config.Validate` **拒绝启动**；daemon 的 `RequireAuth` 对任何非回环监听恒为 `true`。见 `07` §1。
- **敏感请求头不落库**：`Authorization` / `Cookie` / `X-Api-Key` 等在 store 两处强制剥离，API 三处写路径直接拒绝（`400 E_INVALID_INPUT`），只允许 `credentialRef`。剥离而非掩码，避免重启后把 `***` 当真实 header 回放。见 `06` §6 / `11` §10。

### 3. 明确 P0 范围边界

**包含**：WBS 1–6；HTTP(S) 直链 Resolver + Range Transport；单调度器 + 唯一 Limiter；SQLite DDL v1 与崩溃恢复；L0 REST/WS/CLI；随机端口 daemon + 本地发现；嵌入式最小 UI；标准 CHANGELOG；CI 与六平台纯 Go 构建。

**不包含**（不得对外宣称已具备）：任何 sidecar / `ffmpeg` / `yt-dlp` / `aria2c`；L1 `/jsonrpc` facade；BT / ed2k / FTP / SFTP / Metalink / HLS / 站点解析 / Telegram / 微信；插件引擎；OS 钥匙串适配器；Flutter/Tauri 正式 UI；L4 互操作与千兆内网性能基准；代码签名/公证/正式发布流水线。

> **时点说明（2026-11-10，WBS 9 后更新）**：本 ADR 描述的是 **P0 基线快照**，
> 「不包含」清单只对 P0 成立。P1 WBS 8 已实现 Metalink v3/v4 + RFC 6249 清单解析与
> thunder/flashget/qqdl **链接解码**；P1 WBS 9 已实现 FTP / FTPS / SFTP Transport 与
> `DirectFile` Resolver（不含 FTP 主动模式、不含迅雷 P2SP、不含公网互操作矩阵）。
> **仍未实现**：BT / ed2k / 站点解析 / HLS / Telegram / 微信 / 插件引擎 / OS 钥匙串
> 适配器 / L1 facade / 正式 UI。当前实现进度以 `CHANGELOG.md` 与 `14` §11 为唯一真值源，
> 不得引用本 ADR 的「不包含」清单作为当前能力声明（**其中 BT / 磁力已于 P1 WBS 7
> 实现，2026-11-10**；其余条目状态见 `14` §11）。
> 同理，上文「实现基线证据」表中的「5 PASS / 1 WARN」与「12 个链接模块」是
> **P0 评审时点**数字，作为已签署证据保留、不改写；WBS 9 后为 13 个门禁包、
> 16 个链接模块；**WBS 7 后为 14 个门禁包、86 个链接模块、
> `make gates-strict` 6 PASS / 0 WARN / 0 FAIL**，见 `docs/README` §三 当前态口径。
>
> **2026-11-09 修正**：原先列为「不包含」的 CycloneDX SBOM / `govulncheck` / 许可证扫描 / 覆盖率报告 / 回滚演练属于**构建期门禁工具**，不是产品能力，已在评审准备轮补齐并接入 CI（`make gates`），故从「不包含」清单移出；覆盖率的**阈值当时仍有 8 个包未达标**，见 `17` §5（该债务已于 2026-11-10 清零，见文末「评审后状态更新」）。

**已知的 P0 限制（须写在产品与运维口径中）**：

1. `MemoryCredentialStore` 是进程内参考实现，`mem://` 引用在 daemon 重启后失效，受影响任务需重新提交凭据。`core.CredentialStore` 接口已为 OS 适配器预留。
2. `tasks.input` 落库前经 `RedactURL`，但进程内存仍持有未脱敏原始输入（功能必需），靠「不写日志 / 不进事件 / 不进响应」约束。
3. `security.allowLoopbackForDev` 是显式降级开关，仅允许与回环监听组合；公网目标仍走完整白名单。
4. 非回环监听仅 Bearer 鉴权，无 TLS / 用户体系 / Origin 校验，须置于受控网络或反向代理之后。
5. 最小 UI 是契约验证占位件；OPEN-02 当时未决（2026-11-09 已定档 Flutter，见文末「评审后状态更新」）。

### 4. 变更同步规则

任何代码更新必须同时：① 写入根目录 [`CHANGELOG.md`](../../CHANGELOG.md) 的对应分组；② 同步受影响的 `docs/` 文档（版本/状态头 + 变更说明）；③ 若触及架构约束，更新本 ADR 或新增 ADR；④ 跑 `python3 tools/build_docs.py` 重建门户并用 `--check` 校验 0 断链。此规则已固化为 `15` §10。

## 备选方案（含否决理由）

| 方案 | 否决理由 |
|---|---|
| 把实现改回 `05` v0.1 的旧接口 | 会让 `core` 反向依赖 `internal/security`，并让 Transport 拥有第二套分片状态，直接违反 ADR-0002 单调度器 |
| 用空壳包/桩实现填满 `05` §1 的目标目录树 | 会让「已实现能力」与「目录存在」混淆，`/capabilities` 与产品文案容易误报；P0 选择不创建空包 |
| 把所有 P0 取舍分散写进各文档脚注 | 缺少单一归档点，评审时无法一眼判断哪些是「有意不做」、哪些是「漏做」 |
| 把 CHANGELOG 合并进 `docs/14` 变更记录 | 不符合 Keep a Changelog 规范，也不利于发版比较链接；用户明确要求独立的标准更新日志文档 |
| P0 直接接入 OS 钥匙串 | 会引入 cgo 风险与三平台 CI 复杂度，拖慢关键路径；接口先行、适配器后置（ADR-0015 边界） |

## 后果（正面 / 负面 / 后续动作）

**正面**：规范与实现可逐条对齐；评审有明确的「已完成 / 有意不做」清单；后来者不会把范围外能力误判为缺陷；所有偏差都有测试或静态守卫兜底。

**负面**：P0 产物不能作为面向终端用户的完整下载器交付；凭据不跨重启会实际影响体验；文档需要长期维护「目标 vs 现状」双层表述。

**后续动作（P1 优先队列）**：OS 钥匙串适配器 + 凭据跨重启；`events` 保留期清理与 `chunks` 批量刷盘聚合；慢启动动态扩连；`POST /tasks` 响应内嵌 `Resource` 预览；~~**8 个包的覆盖率补测并把 `gates.py --strict` 接入 CI**~~（2026-11-10 已完成）；L4 互操作与千兆内网性能基准；（OPEN-01 许可证、OPEN-02 UI 与 P0 里程碑正式评审均已于 2026-11-09 完成，见文末「评审后状态更新」）。

> **2026-11-09 评审准备轮更新**：CycloneDX SBOM / `go mod verify` / 许可证扫描 / `govulncheck` / 覆盖率报告 / 回环吞吐回归基线 / 备份回滚演练已由 `make gates` 落地并接入 CI，不再是 P1 待办；首次扫描发现并修复 Go 1.27.2 的 `GO-2026-6809`（工具链升 1.27.3）。评审材料见 [17](../17-P0里程碑评审材料.md)；本 ADR 已于 2026-11-09 随 P0 里程碑评审转为 `Accepted`。
