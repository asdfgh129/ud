# ADR-0002 采用 Resolver → Resource → Transport 统一流水线与单调度器

- **状态**：Proposed
- **日期**：2026-11-08
- **决策者**：架构组
- **关联**：`04` §2/§4/§5、`05`、`07`、`03` FR-TRN-09

## 背景

原始需求混了三类完全不同的东西：① 传输协议（HTTP/FTP/BT/磁力/ed2k）；② 链接封装格式（`thunder://`、Metalink，只是「真实 URL + 校验信息」的容器）；③ 内容源解析器（视频网站、Telegram、微信，本质是「把页面/会话解析成带 Cookie/Header 的流地址」）。若按「一协议一实现」堆叠，队列、限速、断点、进度会被实现多遍，且每加一个来源就要重做调度。

第二个风险来自调度权分裂：aria2 之类的组件不是被动协议代码，它自带 GID、队列、限速、断点与文件布局。一旦让它承担任何实际传输，就出现第二个任务生命周期管理者。

## 决策

1. 所有输入统一走 `输入 → Resolver → Resource → Transport → 落盘 → PostProcessor`。
2. 第 ② 类与第 ③ 类由 `Resolver` 处理，只产出描述、不下载、不写文件；第 ① 类由 `Transport` 执行。
3. `Resource` 是流水线中枢，携带目标、多文件布局、镜像、校验、凭据引用、协议身份、后处理规格。
4. **调度器唯一**：只有 Go 核心 `Scheduler` 拥有 Task 状态机、队列、并发、限速、重试、文件布局与进度。`Limiter` 是唯一速率权威。
5. 任何外部进程/库不得自行管理任务生命周期；「HTTP 自研 + BT 外包」这类混合归属明确禁止。

## 备选方案

| 方案 | 结论 |
|---|---|
| A. Go 全自研单调度器 | ✅ **采用** |
| B. 把整个引擎交给 aria2，Go 只做 Resolver + RPC 适配（Motrix 路线） | 自洽，但 RPC 黑盒、GPL、移动端不可达；仅适合「几个月出 MVP、开源、只做桌面、无 Go 协议经验」的团队。若选 B 必须**连 HTTP 一起交出去** |
| C. 只把 BT 交给 aria2 | ❌ **最差**：双调度器，全局限速 2+2=4MB/s、并发两套上限、SQLite ↔ `.aria2` 双真值源、落盘布局不统一、崩溃后按 GID 重建。省下的 BT 开发量会在状态同步上加倍还回来 |

## 后果

**正面**：队列、限速、断点、进度、重试、去重只实现一次；新增网站 = 新增 Resolver 插件；新增协议 = 新增 Transport 后端；进度与状态可直接映射对外 API。

**负面**：`Resource` 模型复杂度前移到 P0（见 ADR-0013）；纯 Go 实现 HTTP 分段、BT 接入等有初始开发量；对团队协议栈能力有要求。

**后续动作**：P0 定死 `Resource` / `Resolver` / `Transport` / `PostProcessor` 接口（`05`）；全局限流唯一实现；若未来启用 BYO 适配器，预算由核心分配后下发，禁止其自读配置。

## 合规与验证

- CI 静态检查：代码中不存在第二处全局速率配置读取（`15` §2）。
- 集成测试：全局限速设为 X 时，任意数量与任意协议组合的任务总吞吐 ≤ X（`12` 故障注入与性能基准）。
- 取消任务能可靠终止全部子进程与分片写入。
